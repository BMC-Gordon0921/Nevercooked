## 双角色最小切片（本轮完成）

按第 1 项建议落地，但形态与最初设想不同：用户否决了「准星点名 + 两步队列」，理由是 AI 帮厨的目标就是提高自动化水平，不该再要玩家下命令。现行做法是让帮厨成为**第二个 `Brain`**，与玩家共用一套输入、交互与寻路，靠共享租约（`game/systems/tasking.py`）分工；玩家唯一的管理杠杆是设置里的档位/倾向与局内 `Y` 键。

| 验收 | 结果（挑战难度、180 秒） | 证据 |
|---|---|---|
| A1 玩家挂机，帮厨独立出餐 ≥8 单 | seed 7 出餐 15 单，`world.validate()` 为空 | `tests/coop_accept.py` A1 |
| A2 积压被消化 | 玩家走开：单人队列峰值 8 张、跑单 5、出餐 0；双人队列峰值 0、跑单 0、出餐 15 | A2 |
| A3 玩家在砧板上干活时帮厨不插手 | 3 秒内 0 次砧板交互，租约仍是 `player` | A3 |
| A4 同一张票最多一位主人，全程校验干净 | 60 秒内 5 张票，无重复认领，validate 干净 | A4、`tests/helper.py` |
| A5 争用有明确反馈 | 玩家按 F 抢帮厨在用的蒸笼 → `reject`，提示「帮厨正在用这台蒸笼」 | A5 |
| A6 双人吞吐 | strong 806.8 → 806.8（+0.0）；relaxed 381.2 → 601.6（+220.4） | A6、`tests/coop_speed.py` |
| A7 双人局不计成绩 | 默认关闭；`record_coop` 只加 `coop_runs`，不动最佳分与解锁 | A7 |

关键结论：厨房是**到单上限**而不是厨师速度上限（蒸笼占用 26–40%、队列峰值 0、活跃单 1.1–1.3），所以强代打时第二个厨师无单可接，只有对真人或慢一点的玩家才有 +220 的价值。被实测否掉的方案：玩家侧公平门（−41.6）、提前蒸饭（−48）、帮厨快速放弃（均值 649.8）、`学徒/熟手` 档位（10 种子 500.5 对 493.5，仅手感差异）。

遗留：帮厨档位目前只有「补单 / 辅助」两种倾向与两档熟练度，没有「只做切配」这类细分工；局域网同步、经营闭环（钱包 + 3 个升级）仍是下一步。

## 下一步建议（顺序与验收）

1. ~~**双角色最小切片**~~（已完成，见上一节：自主帮厨 + 共享租约，A1–A7 通过）。不做点名队列——自动化是目标，不是代价。
2. **局域网合作切片**：在双角色本地验证后，建立主机权威的输入与状态同步。验收：两台机器移动、拿放、出餐、结算一致，持续 30 分钟；明确掉线处理。此阶段验证原策划的核心承诺。
3. **经营最小闭环**：先持久化钱包，做 3 个升级而非一次铺满 16 节点。验收：完成一局、购买升级、下一局效果可观察；退出重开仍保留；不能重复结算刷钱。避免升级污染独立挑战模式的基准。
4. **内容扩展**：先从 3 道增至 6 道，新增一张有明确分工路线的图；再引入一种空间机制。每道新菜须有工序、引导、资产与端到端出餐验证。完成后再决定余下机制与对战排期。
5. **交付验证贯穿每步**：找 5 位未玩过的人测试前三分钟，记录首次出餐时间、失败交互位置和暂停/退出是否可发现；在干净机器验证启动包；保留固定 seed 回归与真实试玩两套证据。

本次建议不改变原策划的产品方向。下一次最有价值的开发任务是第 1 项，继续追求代打 900 分或扩充美术工具不能补上合作与经营的缺口。
